# Designing useful alternatives

Read [design-diagnostics.md](design-diagnostics.md) and [execution-contract.md](execution-contract.md). A round gives
an owner useful alternatives for the same product and content, not a collection of arbitrary skins.

1. Select the screens that expose the product's important visual decisions. Three is the default, not a mandated
   list/home/core/peak story. Reuse a meaningful flow and identical required content.
2. Ground ideas in product truth, an existing brand, reference system or real-world vernacular. Name the source and
   the translation into UI. Familiar components are allowed and can be essential.
3. Oversupply through complementary lenses. Normal/thorough may split explicit source groups, with approximately 1.7× candidates. Do not ask one proposer to
   invent an entire large round from a single mental model.
4. Select for the requested comparison. Use a compact matrix of meaningful axes (composition, typography, density,
   imagery, color, containment, emphasis); compare nearest pairs. Caps are optional product-specific tools, never
   universal color/font/hero quotas. Honor explicit family constraints and explain limited axes.
5. Give each selected direction a buildable card: thesis, signature, roles/colors/type, fixed-screen compositions,
   assets and trade-offs. Coherent execution matters more than adding novel accessories.
6. Keep boards and screens consistent. A board explains thesis, demonstrates the signature on real data, shows
   palette roles and type, and admits costs. Include only claims the actual screens support. Size the board for its
   target; HTML boards align to the device row, Figma boards remain native editable frames.
7. Inspect rendered screens individually and in matching-screen comparisons. Distinction can be structural or subtle
   depending on the user's question. Desaturation is an optional diagnostic, not a mandatory pass/fail metric.
8. Fresh critique names substantive evidence and bounded repairs. Do not force numeric aesthetic scores or change
   every variant after a clean pass. Run one repair/verification cycle, then report remaining issues honestly.

Later rounds follow explicit feedback. Keep preserves what was selected; it does not authorize more screens, motion,
edge states or another mode. Unmentioned variants remain undecided. When a direction is selected, extraction records
its useful tokens, components and signature rules plus open issues for a later implementation workflow. It does not
implement the product or imply a production-ready design system.
