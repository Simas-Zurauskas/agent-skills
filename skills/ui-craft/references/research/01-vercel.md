## 2. Per-source rules and techniques

### 2.1 Web Interface Guidelines (sources 1, 2, 3, 4)

**Packaging.** Three artifacts from one repo:
- `README.md` = the human page (also vercel.com/design/guidelines). Prose, sectioned: Interactions, Animations, Layout, Content, Forms, Performance, Design, then "Vercel-specific" (Copywriting).
- `AGENTS.md` = "Concise rules for building accessible, fast, delightful UIs. Use MUST/SHOULD/NEVER to guide decisions." Meant to be dropped into a repo's agent instructions so it applies while writing code.
- `command.md` = a slash-command/review prompt: "Review these files for compliance: $ARGUMENTS ... Output concise but comprehensive—sacrifice grammar for brevity." Groups findings by file as `file:line - issue`, prints "pass" for clean files.
- `agent-skills/skills/web-design-guidelines` wraps command.md as a skill. It says "Read that file before each review. Do not fetch rules from the network" and pins a commit and SHA-256 (changed 2026-10-29 from fetching main at runtime).

**Gap that matters for us.** The review file (command.md, and therefore the skill) does NOT contain the visual-craft rules. I grepped: "Layered shadows", "Nested radii", "Optical alignment", "Hue consistency", "APCA", "Skeletons mirror", "Deliberate alignment" appear in AGENTS.md and README but have 0 hits in command.md. README also has rules in neither agent file ("Minimum loading-state duration ~150-300 ms show-delay, ~300-500 ms minimum visible"; "Subset fonts"; "Text anti-aliasing & transforms"). So the installed skill is mostly an accessibility/interaction/performance linter; if we want the craft rules we must take them from AGENTS.md/README.

**Rules most relevant to craft (exact, from AGENTS.md / README):**
- Design: "Layered shadows (ambient + direct)"; "Crisp edges via semi-transparent borders + shadows"; "Nested radii: child ≤ parent; concentric"; "Hue consistency: tint borders/shadows/text toward bg hue"; "Meet contrast—prefer APCA over WCAG 2"; "Increase contrast on :hover/:active/:focus"; "Match browser UI to bg" (theme-color); "Avoid dark color gradient banding".
- Layout: "Optical alignment; adjust ±1px when perception beats geometry"; "Deliberate alignment to grid/baseline/edges—no accidental placement"; "Balance icon/text lockups (weight/size/spacing/color)"; "Verify mobile, laptop, ultra-wide (simulate ultra-wide at 50% zoom)"; avoid unwanted scrollbars (macOS "Show scroll bars: Always" to test).
- Content: "Skeletons mirror final content to avoid layout shift"; "Design empty/sparse/dense/error states"; "Resilient to user-generated content (short/avg/very long)"; "No dead ends"; "Inline help first; tooltips last resort"; "tabular-nums for number comparisons"; "Non-breaking spaces: 10&nbsp;MB, ⌘&nbsp;K"; curly quotes; `…` not `...`; `text-wrap: balance`.
- Animation: "Animate only to clarify cause/effect or add deliberate delight" (necessity check); only `transform`/`opacity`; "Never transition: all"; "Correct transform-origin (motion starts where it 'physically' should)"; interruptible; reduced-motion; CSS > WAAPI > JS libs.
- Interaction: hit target ≥24px (mobile ≥44px); "If it looks clickable, it must be clickable"; tooltip delay on first only; URL reflects state; destructive actions confirm or Undo; forms: never block paste, don't pre-disable submit, errors inline + focus first error, placeholders end with `…` and show an example value.
- Vercel-specific (README labels these "preferences ... not universal"): Title Case buttons/headings (sentence case on marketing pages), `&` over "and", numerals for counts, "Error messages guide the exit", "Default to positive language".

**Internal inconsistency worth knowing.** README/AGENTS say mobile inputs must be ≥16px "Or set `<meta name=viewport ... maximum-scale=1>`" while the same lists say "Never disable browser zoom" and command.md flags `maximum-scale=1` as an anti-pattern. Take the font-size route only.

**Novel.** The two-tier honesty (universal vs "Vercel-specific"), and the very concrete micro-craft rules (concentric radii, hue-tinted shadows, optical ±1px). Not novel: it contains no guidance on choosing a direction, so it cannot by itself prevent sameness.

### 2.2 Vercel's own product-design skill (source 5)

This is the strongest official statement on how to make agents produce judged, non-generic UI. Structure published in full:

- Repo layout: root `AGENTS.md` (says when to load the skill) + `.agents/skills/product-design/{AGENTS.md, SKILL.md, references/*.md, exemplars/pr-*.md}` + `tooling/scripts/evals/` (fixtures with before/after, rules-checklist.json).
- References: product-judgment, interface-quality, resilience, surfaces (+ per surface), copy, rules, glossary, patterns, coverage-gaps. Exemplars are shipped PRs, "along with mistakes to avoid".
- `SKILL.md` first resolves a **mode**: Shape / Implement / Review / Copy / Harden, "This keeps audits from becoming edits and copy passes from expanding into redesigns."
- Operating contract lines worth quoting: "Start with the job, not the pixels." "Define the outcome before the output." "Use evidence, not taste." "Treat shipped code as evidence, not automatic precedent." "Choose the smallest coherent intervention." "Decide before decorating." "Design every reachable state." "Verify the real surface... Never claim visual verification from code alone." "Do not add decorative novelty, motion, or copy unless it clarifies structure, state, or brand intent."
- Decision authority order: user goal > verified product evidence > repo-canonical guidance > accepted decisions/exemplars > adjacent shipped patterns > general heuristics.
- Workflow: set scope+mode, load product context, write a compact internal brief (user, job, current behaviour, outcome, success signal, non-goals, object, scope, action, consequence, reversibility, permissions, open decisions), map reachable states, load routed references, decide then implement, verify (lint, compact AND wide viewports, every changed state, keyboard order/focus, long content, RTL risk).
- Review output priorities P0 to P3, each finding with location, verification status, canonical source, user consequence, smallest fix.
- Rules have stable IDs: `rule/destructive-names-action: Destructive CTAs follow Verb + Noun. Never use Confirm, OK, or a bare verb.`
- **Linters for mechanical rules** (examples): no nested modals; radio buttons instead of select for 2-3 static options; accessible names on icon buttons; reject custom focus rings that bypass tokens; "Prevent className from overriding a design-system component's color, radius, or shadow while still allowing layout classes"; replace raw shadows with theme Material classes; "Flag arbitrary spacing that falls off the 4px grid".
- Decision tree: can code identify the failure without rendering? No: agent guidance. Yes and few false positives and concrete fix: linter.
- **Evals:** agent edits a "before" state, a judge scores a rubric; holdouts hide expected edits; fixtures run with and without the skill; "We score rule correctness separately from similarity to the shipped result. Shipped code can contain a flaw that the agent should improve instead of reproduce."
- Writing good rules: "Avoid starting with broad adjectives like clear, polished, or intuitive. Agents need observable decisions. 'Destructive actions use Verb + Noun' is usable. 'Buttons should be clear' is not." Decision record template: Status, Scope, Decision, Rationale, Evidence, Exceptions, Bad example, Good example, Assumptions, Open decisions.
- **Trigger warning:** "agents failed to invoke an available skill in 56% of cases", so put the trigger in persistent repo instructions and "Ask the agent to report which surfaces and references it loaded."
- Governance: weekly evidence intake (collector and judge are separate agents), human approves every rule; "Never promote one screenshot, one shipped file, or one reviewer comment into a universal rule by itself."

**Novel / genuinely useful:** the mode split, the "linter vs prose" tree, "observable decisions" as the quality bar for rules, coverage-gaps file, separating "did it load the skill" from "did it follow the rule". **Limit:** this is about consistency with an existing product and design system. It does not tell an agent how to be original on a blank page; it assumes the system exists.

### 2.3 vercel.com/design.md (source 7) and its write-up (source 6)

Closest thing in this track to an anti-slop guide. Facts:
- It is a single agent-readable skill file for building Vercel-branded report pages in any tool, plus a public stylesheet (`vercel.com/geist/vercel-brand.css`, class prefix `vbg-`) so "agents kept inventing their own typography, spacing, and layout, so we took those decisions away from the model entirely." The agent documents class names and never reads the CSS (saves context).
- Failed first attempt: porting product-design into one prompt. "every model reading it interpreted that description differently". Words alone ("keep the layout clean") do not transfer; they rewrote from scratch against fixed evals.
- Eval method: 7 fixed scenarios (usage report, renewal proposal, benchmark report, planning page, build-vs-buy brief, security brief, deck) with frozen mock inputs and viewport; rounds on Claude and Codex; a local blind A/B review app; each reviewer correction stored against the run; corrections go to the "narrowest place": prose rule, stylesheet primitive, or deterministic check. 200+ runs. Result: first-attempt pages had 39 known failures with the file vs 91 without (57% fewer), but the authors state the checks only catch failures already written down, n=6 pages, and every page "still had at least one failure serious enough to block shipping". Honest, and an important calibration.
- Observed effect: without the file the model "generated a generic SaaS dashboard"; with it the page led with the recommendation, put peers on one scale. It changed structure, not just styling. And "design.md wasn't pushing every page toward one template."

Rules in the file worth lifting (all quotes short; the file is brand-scoped, so judge each for our context):
- Process: frame the reader's job (who, context, decide what, strongest answer, evidence, caveat). "Privately name the obvious layout the artifact category would suggest. Reject it unless the material earns it." "privately compare two materially different composition hypotheses before coding. Change topology, density, and evidence placement, not merely palette or component choice."
- "Give every artifact one evidence-bearing organizing move that belongs to its material and could not be transplanted unchanged into an unrelated report."
- Squint test and text-mask test (blur the words; hierarchy should still read). "If every block has equal weight, redesign before coding."
- "Create presence through commitment, not additional effects." "Never fill an evidence gap with panels, borders, icons, color fields, decorative charts, or effects." "Diagnose quantity separately from intensity": busy means remove/combine; loud means reduce colour, scale, weight, borders, motion.
- "Design in monochrome. Use color only when it adds significant meaning." "Establish hierarchy through typography before surfaces or color." "Prefer spacing, alignment, typography... before borders or boxes." "Do not wrap every section, metric, or comparison in a card."
- Gap ownership: each gap has one owner; "Do not repair one awkward transition with an arbitrary one-off margin; repair the grouping or spacing owner."
- Equivalent peers share type role, size, weight, numeric treatment. Prose 60-68 characters per line. Tables full width, numeric headers right-aligned like their cells, body cells baseline-aligned. Direct labels over legends. Repeated bars share one scale and one grid.
- Motion: "Default to stillness." No marquees, simulated typing, pulsing status dots, parallax, scroll reveals on every section.
- Media: no stock imagery, decorative AI illustrations, abstract shapes, fake screenshots; no decorative icon tiles.
- **"Reject generated-design reflexes" list (verbatim items):** all-caps/tracked eyebrows and numbered section labels; em dashes; decorative gradients, glows, blobs, stripes, textures, glass, ornamental shadows; "Generic centered hero copy followed by a card grid"; repeated metric boxes; badge/pill for ordinary metadata; cards nested in cards or "borders used to repair weak hierarchy"; "A dark rounded rectangle around every chart"; arbitrary icon tiles; tiny muted prose; "Identical section silhouettes across unrelated reader questions"; repeated recommendation/summary/conclusion saying the same thing; authoring-process narration; visible theme toggles.
- Counter-warning in the same file: "Do not compensate for avoiding these defaults by producing a sterile anti-design template. Vercel restraint is precise hierarchy, excellent typography, clear evidence, strong alignment, and deliberate tension. It is not merely black, white, thin rules, and large empty margins."
- Review pass order: first read, language, composition, typography, evidence, restraint ("Can any surface, border, pill, icon, label, color, paragraph, or section be removed without losing meaning, affordance, or rhythm?"), themes/reflow, trust/access. "Render the actual result... both light and dark".

**Caveat:** This file's taste is Vercel's (restrained, monochrome, editorial, report pages). A wedding-invitation product wants warmth and ornament; several bans (eyebrows, pills, gradients, ornament) are brand choices, not universals. What transfers is the method: name the defaults, compare two compositions, one organizing move, remove-test, fixed-scenario evals.

### 2.4 AGENTS.md vs skills (source 8)

Next.js 16 API evals: skill never invoked in 56% of cases; skill with default behaviour 53% = baseline (no docs) 53%; skill with explicit "invoke" instruction 79%; an 8 KB docs index in AGENTS.md 100%. Wording of the trigger instruction changed outcomes a lot ("invoke first" missed config changes that "explore first" got). Implication for us: do not rely on a description-only skill trigger. Put a one-line trigger in CLAUDE.md/AGENTS.md ("Before building or changing UI, load X") and keep the always-needed rules (ban list, the 5-10 key decisions) in the persistent file. Caveat: measured on docs retrieval in early 2026, not on visual design.

### 2.5 v0 official prompting and design systems (sources 9, 10, 11, 12)

- Prompt template: "Build [product surface: components, data, actions]. Used by [who], in [what moment], to [what decision or outcome]. Constraints: platform/device, visual tone, layout assumptions." Three inputs: product surface, context of use, "constraints & taste". "v0 optimizes for assumed usage. If you don't define the context of use, it will guess." "Constraints tell v0 what not to invent." Their tests: detailed constraints produced "mobile-first" rather than "desktop layout that shrinks", with intentional colour coding and fewer lines. Cheap and sound, but "Professional but approachable... Make it feel like a real SaaS product" is exactly the kind of adjective that yields the median look.
- Iteration: prompt for logic/structure; Design Mode (visual picker) for colours/spacing/type.
- Design Systems 2.0: a design system is saved as a **skill** with `v0.json` (reference sources, starter app path), built from package, consumer app, Storybook/docs, Figma frames, notes. Rules: "v0 grounds itself in the real source. If a component, prop, or token cannot be verified from the sources, v0 should not use it." Notes field for "Deprecated components, anti-patterns, or gotchas". "Take the review seriously": the saved starter app is inherited by every later app, so a flaw is replicated. Include a real consumer app; "Prefer current docs, current package versions, and working examples over exhaustive but stale references." Update on each release.
- Legacy registry guide (still live): "v0 is specifically trained on the default implementations of the shadcn/ui components and may struggle with any customizations." So heavy rewrites of primitives can degrade v0 output; customise tokens first. (This applies to v0's own model, not to our Claude agents.)
- Packaging pattern for us: design system = skill + working starter app + consumer app reference + anti-pattern notes.

### 2.6 Leaked v0 system prompt (source 13; UNOFFICIAL)

Section "Design Guidelines" (as of the May 2026 revision of the leaked file):
- Colour: "ALWAYS use exactly 3-5 colors total": 1 primary, 2-3 neutrals, 1-2 accents; "NEVER use purple or violet prominently, unless explicitly asked for"; "Avoid gradients entirely unless explicitly asked for"; if used, subtle, analogous (blue to teal, not pink to green), max 2-3 stops; override text colour whenever you override a background.
- Type: max 2 font families (heading + body); body line-height 1.4-1.6; never decorative fonts for body or text below 14px; wrap titles in `text-balance`/`text-pretty`.
- Layout: mobile-first; flex first, grid for 2D; no floats/absolute unless needed; Tailwind spacing scale, `gap-*` not `space-*`; never mix margin/padding with gap on the same element.
- Tokens: semantic design tokens only; "DO NOT use direct colors like text-white, bg-white, bg-black"; set the background class on `<html>`; fonts via `next/font` in layout.tsx and `font-sans/serif/mono` classes. "Design tokens are a tool to help you create a cohesive design system. Use them while remaining creative and consistent."
- Visuals: "Use images to create engaging, memorable interfaces"; "NEVER generate abstract shapes like gradient circles, blurry squares, or decorative blobs as filler"; no hand-drawn SVG illustrations; no emojis as icons; consistent icon sizes 16/20/24.
- **Final Rule: "Ship something interesting rather than boring, but never ugly. Utilize the GenerateDesignInspiration tool before any design work."**
- The `GenerateDesignInspiration` tool (Tools.json): inputs `goal` and optional `context` (brand adjectives, constraints). Use for vague requests ("a nice landing page"), when no direction exists, complex multi-section UX; skip for backend, small tweaks, detailed mockups, clones. "If you generate a design brief, you MUST follow it." The prompt's examples call it in parallel with codebase exploration, then build "following the detailed design brief". I.e. v0 separates "art-direct" (a design brief step with a distinct palette, type, interactions) from "implement". A mandatory brief step before code is the technique to copy.
- History (source 14, 2024): v0 then said "DOES NOT use indigo or blue colors unless specified". By 2026 the ban moved to purple/violet. The banned colour tracks whatever the model over-produces.
- Limits: the leaked rules are blunt numeric caps (5 colours, 2 fonts) that guard against chaos, not instruments of originality. v0 still gets criticised as generic (source 23).

### 2.7 shadcn as the AI default (sources 15, 16, 17)

- Maintainer admission (2025-12-12): "But somewhere along the way, all apps started looking the same. I guess the defaults were a little too good. My bad." Fix: `npx shadcn create`: "Customize everything. Pick your component library, icons, base color, theme, fonts"; config "doesn't just change colors, it rewrites the component code" (spacing, structure, libraries). "It's time to build something that doesn't look like everything else."
- Styles (geometry the CSS variables cannot reach): `vega` classic; `nova` compact, hairlines; `maia` soft, rounded, generous; `lyra` boxy, sharp, pairs with mono; `mira` dense; `luma` rounded, soft elevation, "inspired by macOS Tahoe, minus the glass"; `rhea` compact luma; `sera` editorial/typographic serif display (named in the skill's table). Presets are short codes encoding style, baseColor, theme, chartColor, iconLibrary, font, fontHeading, radius, menuAccent, menuColor; `preset decode/resolve/url/open`, `apply <code> [--only theme,font]`. Base UI default since 2026-07-02; Radix still supported.
- Skill (`npx skills add shadcn/ui`, `user-invocable: false`, activates on `components.json`): injects `shadcn info --json` (framework, Tailwind version, base, style, iconLibrary, aliases, installed components). Critical rules: use existing components first; compose, don't reinvent; built-in variants before custom styles; semantic colours (`bg-primary`) never raw (`bg-blue-500`); "`className` for layout, not styling. Never override component colors or typography"; no `space-x/y-*`; `FieldGroup`+`Field` for forms; Dialog needs a Title; `Empty`, `Skeleton`, `Badge`, `Alert` instead of custom divs; run `shadcn docs <component>` before using one; review every added component for violations; never guess the registry; never overwrite components without approval.
- **design-system.md ("Design Systems from DESIGN.md")**, the best procedure for non-generic shadcn: scaffold with a preset; install all components; read the DESIGN.md frontmatter plus Do's/Don'ts/Known Gaps; map tokens onto shadcn variables (keep hex if the spec gives hex, don't convert to OKLCH); pin radius scale in `@theme inline`; override shadow scale verbatim (set `--shadow-xs` to none for hairline-only systems); install the named brand font substitutes; turn every type token into a `type-*` utility with clamped display sizes and em tracking; derive dark mode honestly and say so; match the documented focus treatment; restyle by editing `cva` variants while keeping variant names; "Control heights move together" across button/input/select/etc.; "Turn each 'Don't' into a check before you finish"; follow documented states exactly ("darken on press only" means `active:` not `hover:`). Verify: typecheck, no console errors, no horizontal overflow at 375 and 1280, screenshots of hero/foundations/form/dark band compared to the spec, toggle dark mode.
- **design-system-page.md**: build a showcase page: colour roles as contrast-measured pairs ("A brand primary at 3:1 behind 14px labels is a real finding"), type specimens, pinned state matrices (hover/focus/pressed side by side), edge cases (long text, empty, error, loading, missing image), rendered do/don't pairs, a coverage script (`scripts/showcase-coverage.mjs`) that lists components no showcase file imports. Evidence-based review of a system, not just a theme.
- Typeset (2026-07): one CSS file with three controls (size, leading, flow) to style prose consistently, "fits its container", reads app tokens.
- Registry/MCP: `npx shadcn@latest mcp` lets agents search/browse/install from any registry (shadcn, third-party, private). Independent test (Supernova blog, secondary, 2026-10-21): agent used MCP to install `AlertDialog` and still hand-built its own destructive-confirm pattern in 3 of 3 runs; MCP supplies the catalogue, not your team's decisions. So registry access does not give taste.

**The "everything looks like shadcn" critique (secondary, 2026):** Krebs lists "shadcn/ui" and "Glassmorphism" under CSS patterns; weekendmvp notes a fresh `shadcn init` writes the same neutral greys and `0.625rem` radius into `globals.css`; dev.to author makes the Tailwind default palette fail the build by replacing rather than extending `theme.colors`. Common fix: change `globals.css` tokens first (palette, two fonts, radius, shadows), leave component signatures intact (so future prompts keep working), add an explicit ban list to AGENTS.md. My assessment: the maintainers' own fix (create + styles + presets) and the critics' fix agree; the missing piece is deciding the direction before touching tokens.

### 2.8 Geist (source 18)

Only concrete system rules, no originality guidance, and it is Vercel's own look:
- Colour: 10 scales (backgrounds, gray, gray-alpha, blue, red, amber, green, teal, purple, pink), 10 steps each with fixed roles: 100 default bg, 200 hover bg, 300 active bg, 400/500/600 default/hover/active border, 700/800 high-contrast bg, 900 secondary text, 1000 primary text. Two page backgrounds, use Background 1 mostly. "Draw each border once." "Keep material shadows translucent" (opaque shadows leave a gray halo). Solid gray by default; gray-alpha only when the background should show through.
- Materials: surface (base/small/medium/large; radius 6/6/12/12), floating (tooltip 6, menu 12, modal 12, fullscreen 16); only tooltips get a stem. Elevation is a named preset, not ad-hoc shadow values.
- Type: roles as classes (heading-72 down to 14, copy, button, label) bundling size, line-height, tracking, weight; Strong/Subtle via `<strong>`. Geist Sans/Mono/Serif/Pixel at vercel.com/font. Pattern worth copying: a fixed role-based type scale and fixed elevation presets, so the agent picks from a vocabulary.
- Note from critics: Krebs counts Geist among fonts LLMs over-pick; Geist is also v0's own example font. A distinctive product should not default to it.

### 2.9 Emil Kowalski skills (sources 19, 20; community, ex-Vercel)

- Thesis: "Agents don't have great taste... All these small things compound." Skills list "all the little mistakes agents can potentially make and explain how to fix them." Method: "If you know what great feels like, describe the rules, then give them to your agents... Almost every 'taste' decision has a logical reason". Be strict: lookup tables, flowcharts (easing decision tree: enter/exit = ease-out; on-screen move = ease-in-out; hover = ease; constant = linear), durations (micro 100-150ms, tooltips/dropdowns 150-250, modals/drawers 200-300; UI under 300ms; exits ~20% faster), "never animate from scale(0), start at 0.95", `scale(0.97)` on `:active`, popover `transform-origin` at trigger, skip delay on subsequent tooltips, semi-transparent shadow instead of solid border, prose max ~65ch.
- `learn-taste` skill: every user correction becomes a rule with its why. Hard rules: only the user's taste; "Never invent a why"; propose then stop; "A check beats a sentence" (lint/test over prose); write for an agent that wasn't there. Corrections are mined from five signals including silent edits and repeated nudges. Rule level: class, not instance or universal. Output goes to `DESIGN.md` plus a one-line pointer in CLAUDE.md/AGENTS.md ("Before building or changing UI, read DESIGN.md").
- `prototype` skill (divergence): build 3 (max 5) genuinely different versions behind a switcher. "Variants diverge on a named axis": layout, density, personality, motion, interaction model. "If two proposed directions would differ only in accent color or copy, they are one direction; replace one." Names describe the direction ("Quiet", "Editorial", "Dense"), never A/B/C. Every variant is fully working with realistic content and meets the same craft bar. Same idea as design.md's two-composition rule but for components.
- `break-ui`: attack the UI with worst-case data. `pick-ui-library`: don't hand-roll toasts or install abandoned packages. Frequency-aware motion ("remove-animations": no motion on keyboard shortcuts or high-frequency actions).
- Credibility: widely used (59k stars), concrete, values-based; but it is one person's taste and mostly motion/polish, less about overall visual identity.

### 2.10 Krebs slop research (source 21; community, primary data)

16 patterns by DOM/CSS check, no LLM judge: fonts (Inter everywhere; Space Grotesk / Instrument Serif / Geist combos; serif-italic accent word in an Inter hero), colour ("VibeCode Purple"; permanent dark mode with mid-grey body and all-caps labels; barely-passing dark contrast; gradient everything; big coloured glows), layout (centered hero; badge above H1; coloured top/left borders on cards; identical icon-topped feature cards; numbered 1-2-3 steps; stat banner rows; emoji-icon nav; all-caps headings), CSS (shadcn/ui; glassmorphism). 22% of 1,590 Show HN pages hit 4+ patterns, 32% hit 2-3, 46% hit 0-1; ~5-10% false positives on manual QA. His own verdict: "Not really [bad], just uninspired." Usable directly as an automated check (`design-slop-cop` repo, scanner at slopcop.adriankrebs.ch; I did not run it).

## 3. For our anti-slop skill

Tag key: [WIG] web-interface-guidelines, [PD] Vercel product-design blog, [DM] vercel.com/design.md + blog, [AM] AGENTS.md-vs-skills blog, [V0] v0 official docs/blog, [V0L] leaked v0 prompt (unofficial), [SH] shadcn, [GE] Geist, [EK] Emil Kowalski, [KR] Krebs.

### 3.1 Process steps

1. **Art-direct before code, as a separate step with a written brief.** v0's prompt makes a design-brief step mandatory before any design work and requires following it ([V0L], unofficial, but consistent with [DM]). Brief = reader/user job, one-sentence stance, palette, type pairing, shape language (radius, border vs shadow), density, one organizing move.
2. **Frame the reader's job first** (who, in what moment, deciding what, strongest answer, evidence, caveat) [DM][V0 prompt template]. Start with the job, not the pixels [PD].
3. **Name the obvious layout for this category, then reject it unless the material earns it** [DM].
4. **Compare two materially different composition hypotheses before coding** (change topology, density, evidence placement, not palette) [DM]. For single components, build 3 variants on named axes behind a switcher and make the human pick [EK prototype]. Two variants that differ only in colour count as one.
5. **Give each artifact one organizing move specific to its material** that "could not be transplanted unchanged" into another product [DM].
6. **Pick a mode** (Shape / Implement / Review / Copy / Harden) so audits do not turn into edits and polish does not turn into redesign [PD].
7. **Decide IA, component semantics, interaction and states before styling** ("Decide before decorating") [PD]. Design every reachable state (loading, empty, sparse, dense, error, permission, disabled, destructive) [PD][WIG].
8. **Set the direction in tokens, not component rewrites.** Start from a non-default shadcn style/preset (`maia`, `lyra`, `luma`, `sera`, ...), then replace palette, fonts, radius scale, shadow scale in the theme file; edit `cva` variants only where geometry demands; keep variant names and component APIs [SH design-system.md][V0 legacy docs]. Control heights change together [SH].
9. **Constrain the mechanics, free the judgment.** Publish a vocabulary (type roles, spacing tokens, elevation presets, allowed classes) so the agent chooses from it and cannot invent arbitrary sizes [DM stylesheet][GE materials/typography]. Keep judgment in prose.
10. **Render and inspect.** Never claim visual verification from code [PD]. Check first viewport, full page, light and dark, compact and wide, every changed state, long/empty/extreme content, keyboard order, scrollbars visible (macOS "always show") [PD][DM][WIG][SH Step 7]. Add break-ui style worst-case data [EK].
11. **Run a removal pass**: "Can any surface, border, pill, icon, label, color, paragraph, or section be removed without losing meaning?" [DM]. Diagnose "busy" (remove) separately from "loud" (reduce intensity) [DM].
12. **Capture corrections as rules with a why**, at class level, and turn mechanical ones into lint/checks [EK learn-taste][PD][DM]. Human approves every rule.

### 3.2 Checkable DO / DON'T rules

Anti-default (these are the "tells"):
- DON'T ship Inter (or any one default) for everything; DON'T use the known LLM combos Space Grotesk, Instrument Serif, Geist, or a serif-italic accent word on an otherwise sans hero [KR]. DO choose a type pairing from the brief and check it renders (our own memory notes known broken Lithuanian faces; this track gives no font test).
- DON'T use purple/violet/indigo wash, gradient-everything, large coloured glows or coloured shadows, gradient text [KR][V0L][DM]. DO use flat grounds and one deliberate accent. v0 caps at 3-5 colours total [V0L].
- DON'T open with centered hero + badge/pill above H1 + three identical icon-topped cards + numbered 1-2-3 + stat banner [KR][DM][V0L-adjacent]. DO make the first viewport carry the central idea or tool [DM].
- DON'T put coloured top/left borders on cards; DON'T nest cards; DON'T repair weak hierarchy with borders or boxes; DON'T wrap every section in a card [KR][DM].
- DON'T use all-caps tracked eyebrows or decorative section numbers [KR][DM] (Vercel-brand; evaluate per product).
- DON'T use emoji as icons; DON'T add abstract blobs, blurry gradient circles, decorative SVG illustrations, stock imagery, fake screenshots, icon tiles as filler [V0L][DM].
- DON'T use glassmorphism by default [KR][DM].
- DON'T leave the shadcn default theme untouched (same greys, same 0.625rem radius) [SH changelog][secondary critics]. DO pin radius scale, shadow scale, fonts, focus style [SH].
- DON'T use raw colour classes (`bg-blue-500`, `text-white`) in shadcn projects; DO use semantic tokens [SH][V0L].
- DON'T let `className` override component colour/radius/shadow; change the variant or token instead [SH][PD lint].
- DON'T narrate the authoring process in page copy; DON'T repeat the same conclusion at equal prominence in several sections; avoid em dashes and "Unlock/Supercharge" copy [DM][weekendmvp, secondary].

Craft (checkable details):
- Hierarchy by type before colour; peers share one type role, size, weight, numeric style; prose 60-68 ch (or ~65ch) [DM][EK].
- Layered shadows (ambient + direct); semi-transparent borders+shadows for crisp edges; concentric radii (child ≤ parent); tint borders/shadows/text toward the background hue; translucent shadows (no grey halo); draw each border once [WIG][GE][EK].
- Optical alignment ±1px; every element aligns to something deliberate; balance icon/text lockup weights [WIG].
- Tabular numerals in number columns; `text-wrap: balance` on headings; curly quotes; `…`; non-breaking spaces in units and shortcuts [WIG].
- Interaction states: hover/active/focus raise contrast; visible `:focus-visible` ring; hit target ≥24px (≥44px mobile); if it looks clickable it is clickable [WIG].
- Motion: default to stillness [DM]; animate only to clarify cause/effect or add deliberate delight [WIG]; `transform`/`opacity` only; never `transition: all`; `prefers-reduced-motion`; interruptible; correct `transform-origin`; ease-out for entering; UI motion under ~300ms; never from `scale(0)`; no motion on frequent actions [WIG][EK].
- States and resilience: empty/sparse/dense/error designed; skeletons mirror final layout; long/short/empty content; no dead ends; destructive actions named (Verb + Noun) and confirmable or undoable; errors say how to fix [WIG][PD].
- Accessibility floor: WCAG AA at least, never colour alone, icon buttons named, semantic HTML before ARIA, skip link, one h1 [WIG][DM]. [WIG] prefers APCA over WCAG 2; I would treat APCA as a supplementary check since WCAG 2 AA is still the compliance baseline (my judgment, not from these sources).
- Charts/tables: zero baselines for length encoding, direct labels over legends, one shared scale, numeric headers aligned with cells, tables full width [DM].
- Data viz of dashboard type is secondary for our product; keep only if relevant.

### 3.3 Evaluation methods this track supports

1. **Fixed-scenario A/B with a saved baseline** [DM]: freeze prompt + mock data + viewport; generate once without the guidance (keep it), once with; shuffle and score blind against a short rubric; "first attempt only, no re-rolls". Their result: 57% fewer known failures, plus honest caveats (small n, only catches written failures). Needs a holdout and multiple trials to claim reliability.
2. **Before/after fixtures with a judge and holdouts** [PD]: score "rule correctness" separately from "similarity to shipped result"; run without the skill to prove the skill changed behaviour; test whether the skill was loaded separately from whether it was followed.
3. **Deterministic slop scoring** [KR]: Playwright script reads computed styles; each tell is a function; bucket by count (0-1 clean, 2-3 mild, 4+ heavy). No LLM judge. Reuse or reimplement design-slop-cop checks for our own screens.
4. **Lint for mechanical rules** [PD]: no raw colours, no `transition: all`, no off-grid spacing, no className colour overrides, no nested modals, icon buttons without names, `outline: none` without replacement. Decision tree: lint if code can detect with few false positives and a concrete fix; otherwise prose.
5. **Design-system showcase page + coverage script + contrast pairs + pinned state matrices** [SH design-system-page.md]; plus overflow check at 375 and 1280, console clean, screenshots of hero, foundations, form, dark band.
6. **Visual human review** against a one-sentence stance plus squint test and text-mask test [DM]; a model-written critique each round is useful but secondary [DM].
7. **Trigger test** [AM][PD]: ask the agent to list which skill/reference files it loaded; test trigger and rule-following separately; put the trigger line in CLAUDE.md/AGENTS.md.
8. **Rule hygiene** [PD][EK]: stable IDs; each rule has scope, why, bad/good example, exceptions; "coverage gaps" list; stricter wording when a rule fails; never promote one screenshot to a universal rule.

### 3.4 Packaging the skill (what this track says works)

- Short `SKILL.md` that routes by mode/surface to focused reference files; keep the always-needed content (ban list, stance, token rules) small and persistent [PD][AM].
- Ship a **bounded vocabulary** (CSS/tokens/classes) plus docs of class names, and tell the agent not to read the CSS [DM].
- Include a **real starter** and at least one consumer example rather than prose alone: "an agent reads product-design surrounded by real components and shipped examples" and prose alone gets interpreted differently by each model [DM][V0 DS 2.0].
- Anti-patterns as a **named list** in the skill: naming patterns helps agents recognise and avoid them [DM].
- Write rules as observable decisions, not adjectives [PD].

### 3.5 Disagreements, tensions, and what looks outdated

- **Fonts:** Krebs lists Space Grotesk, Instrument Serif and Geist as LLM-overused combos, yet Weekend MVP recommends Newsreader/Instrument Serif with Geist/Plus Jakarta Sans as the cure and Developers Digest recommends Geist. Vercel's own file mandates Geist Sans/Mono for Vercel pages. Resolution: any named "safe alternative" becomes the next default; choose from the brief, and rotate/avoid the short lists the models already prefer.
- **Restraint vs ornament:** Vercel's design.md (monochrome, no pills, no eyebrows, no gradients, stillness) and leaked v0 ("ship something interesting rather than boring") pull differently. design.md itself warns against "a sterile anti-design template". For a warm consumer/wedding product, restraint rules are brand-specific, not universal. Keep: remove-test, one focal relationship, hierarchy via type. Drop as universal: bans on ornament, pills, eyebrows.
- **Numeric caps** (3-5 colours, 2 fonts) [V0L] are safety rails, not originality; they can also force sameness. Treat as defaults for a brief-less request only.
- **Customising shadcn:** v0 docs warn its model is trained on default shadcn and "may struggle with any customizations"; shadcn create says it rewrites component code; shadcn's own skill says never override colours via className; critics say override CSS variables and keep signatures. Consistent reading: token-level and variant-level changes yes, API changes no. The v0 warning is about v0's model, not our agents.
- **Skills vs AGENTS.md:** Vercel measured skills not triggering in 56% of cases (Jan 2026, docs-retrieval task); the same team still ships design skills in June/August 2026 and tells readers to put a trigger in AGENTS.md. Test with our own agents; newer models may trigger more reliably.
- **APCA over WCAG 2** [WIG] is the guideline's stance; WCAG 2 AA remains the practical compliance baseline (my judgment).
- **Internal WIG contradiction:** viewport `maximum-scale=1` offered as an alternative to 16px inputs vs "never disable zoom". Use the 16px rule.
- **Title Case for buttons/headings** [WIG] is explicitly Vercel-specific; do not adopt, and note the language is English (our product is Lithuanian; Title Case, `&` over "and", `…` spacing and "numerals for counts" need re-checking for Lithuanian).
- **Possibly outdated:** the 2024 v0 "no indigo/blue" rule (source 14) is superseded by "no purple/violet" in the 2026 leaked file; the legacy registry-based v0 design-systems guide is replaced by Design Systems 2.0 skills; WIG README "Prefer Geist Mono for tabular numbers" vs design.md saying Geist Sans with tabular numerals and Mono only for identifiers (the newer, August 2026 design.md is more specific). Both agent files lag README on a few rules.
- **Evidence quality:** everything Vercel publishes is about consistency with an existing system or brand and about mechanical correctness; none of it demonstrates producing an *original* identity from scratch. The strongest originality techniques here are process-level (art-direct brief, two hypotheses, divergent variants, one organizing move, naming the tells), not rule lists. Numeric results are Vercel's own small-sample evals (n=6 pages for the 57% figure) and should not be quoted as proof.
- **Unverified:** leaked v0 prompt authenticity; I did not run slopcop, the design.md stylesheet, or any of the evals; I did not read Vercel's non-public `packages/geist/STYLE_GUIDE.md` or `design-guidelines`/`review-design-system` skills referenced in the product-design SKILL.md (not published).

### 3.6 Suggested minimal adoptions (my recommendation, weighed against build cost)

1. Persistent rule block in AGENTS.md/CLAUDE.md: trigger line + the named ban list (3.2 anti-default) + "write the brief first".
2. A `brief` step output file (stance, palette, type, shape, density, organizing move) saved before any UI code; ask for 2 composition hypotheses on page-level work and 3 axis-divergent variants for key components.
3. Token-first theming of the chosen shadcn style; pinned radius/shadow/type scale; lint raw colours and `transition: all`.
4. Verify with rendered screenshots (light/dark, 375/1280, states), a removal pass, and a scripted slop check (port Krebs' 16 checks, drop the ones that do not apply to our brand).
5. Adopt the rule format (ID, scope, why, bad/good, exceptions) and a coverage-gaps list; feed every owner correction through a learn-taste style step.
